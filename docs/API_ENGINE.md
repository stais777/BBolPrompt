# 신규 카드 API 엔진 0.4.0

승인된 분리 계획의 여섯 보완항목을 `bbolprom_engine/api_engine/`에 구현했다. 기존 baseline.py/baseline_edits.py/원본 자료/API 공용 근거 함수와 보안·원본 저장 코드는 보존한다. 등록/정상 진입을 확인한 베이스화와 새 API의 의미 정확도는 별도다. **이번 개발은 모의 공급자·임시DB 시험이며 실API·실키·사용자DB를 사용하지 않았다.**

## 사용

1. API 설정에서 **정의 초안 · 교정 이력 열기**. 초안7개는 검토/수정하고 **화면의 정의 확정**으로 확정한다. 초안을 자동 승인하지 않는다. 기존에 사용자가 확정한 정의도 사용한다. 정의가 없는 활성 분류는 실제 호출 대상에서 빠진다.
2. Windows 보관함에 키를 등록하고 계정의 실제 모델ID/현재 단가·일일 한도·외부 전송 동의를 설정한다. 선택 모델의 실제 계정 접근/응답 호환은 확인 전이다. 업그레이드만으로 호출하거나 자동 재시도하지 않는다.
3. 신규 카드를 선택해 **이 카드 API 분석**. API는 인계된 방법·승인 이력과 관련 참고자료로 의미를 판단하고, 앱이 원문/근거·ID·분류·수동 보호를 검증해 저장한다. 최초309개는 분석 대상이 아니다.
4. 신규 카드 태그 직접 수정은 확정/제외 이력에 보존한다. **API · 태그 이력**에서 같은 원문 버전의 태그를 복원한다. 원문·이미지 복원은 기존 **수정 이력 · 복원**과 구분한다.
5. 관련 사용자 교정 참고 옵션은 기본 꺼짐이다. 켜면 다음 유사 신규 카드에 관련 최신 교정의 원문 발췌·태그·제외를 최대3건/8000자 안에서 참고한다. 교정 이력에서 참고 해제/재활성화가 가능하다. 해제해도 현재 카드의 수동 태그는 유지한다. 별도 베이스 사례 옵션은 기존3건/12000자 상한을 유지한다.

## 구현한 경계

- app.py는 신규 처리의 연결부만 전용 Engine/Repository로 위임한다. 베이스 등록/이미지 연결/기준 수동 수정 경로는 그대로다. API 모듈은 베이스 보기/등록 시 초기화하지 않는다.
- 베이스 참고는 읽기 전용 SQLite 연결과 검증된 원본/최신 사용자 수정 스냅샷이다. SQL authorizer는 API 연결의 baseline_*·media·card_media·원문/ID 변경을 거절한다. API 저장은 검증된 신규 cards 행의 태그/상태와 api_* 이력만 처리한다.
- source SHA/태그 버전과 참고한 베이스 수정/분류/교정 버전을 저장 직전 BEGIN IMMEDIATE 안에서 다시 확인한다. 오래된 결과는 적용하지 않는다. 태그·전후 이력·감사는 한 트랜잭션으로 저장하며 감사 저장 실패도 태그 변경을 롤백한다.
- API 전용6테이블: api_card_state, api_tag_editions, api_user_corrections, api_correction_events, api_category_definitions, api_runs. 상태 테이블을 제외한 이력은 append-only다. 기존309개를 이사시키거나 베이스 테이블을 재작성하지 않는다.
- 영문 근거↔한글 태그의 로컬 파생 색인으로 관련 표준을 검색한다. 승인된 세부 태그의 근거로 상위 이름을 조회할 수 있게 연결하고 출처 카드/수정 버전을 기록한다. 검색 결과는 API 참고 후보이며 새 카드 정답을 기계적으로 부착하지 않는다. 추가 유료 임베딩 호출은 없다.
- 현재 유효한 최신 수동 교정만 참고한다. 이전 원문 버전·철회·다른 태그 상태로 복원한 사례는 제외한다. 자동 API 결과를 공통 승인 기준으로 승격하지 않으며 모델 가중치를 학습시키지 않는다.
- 반복 인용은 API가 더 긴 정확한 원문 인용으로 문맥을 특정하게 한다. 여전히 모호하면 임의 위치를 색칠하지 않고 검토 후보로 보존한다. 거짓 인용이 섞이면 부분적으로 유효한 구절만 다시 살려 색칠하지 않는다. 좌표는 앱이 계산하며 기존309의 구간/예외는 변경하지 않는다.

## 보존·백업·실패

기존 신규 카드에서 수동/불명확한 태그는 보수적으로 보호한다. 예전 버전에 남아 있지 않은 삭제 이력은 재구성하지 않는다. 이 업데이트 이후 수동 저장에서 제외 기록과 최신 교정이 생긴다. 보호는 정규화한 태그명과 검증된 표준 식별자를 기준으로 하며, 의미가 비슷하지만 다른 이름인 후보의 실제 판단 품질은 별도 실API 평가가 필요하다.

태그 변경은 API 이력을 저장해 매번 전체 PT/vault ZIP을 만들지 않는다. 최초 스키마 추가 전 DB 전용 `.db-snapshot`을 저장한다. 이 파일이나 태그 이력은 이미지/문서를 포함하는 전체 백업의 대체품이 아니다. 기존 **백업 저장**은 원본 파일·현재DB/API 이력을 함께 포함한다. 원본 삭제·저장소 정리·전체 백업 가져오기 UI 재설계는 이번에 하지 않았다.

키·TLS/목적지·영구 일일 비용/호출 원장은 기존 보안 어댑터를 사용한다. 이미지/전체 PT/전체309 원문은 보내지 않는다. 진단 ZIP은 API 기록의 개수/상태/해시만 추가하고 원문·태그명·근거·키·경로는 추가하지 않는다.

## 검증 범위

전체 자동 검사, 새 API 화면8개, 기존 화면16개와 베이스 수동 태그 화면9개를 구분해 평가 로그/빌드 영수증에 기록한다. 새 API 화면의 공급자는 명시적인 mock이며 실제 요청이 없다. 합성 PT 연결 후 전체309 레코드/이미지 링크가 API 작업 전후 같음을 대조한다. 보호 파일SHA와 직접 SQL 쓰기 차단도 검사한다. 배포 패치는0.3.8/0.3.9 각각에 적용한 파일 해시/사용자data 보존을 검증한 뒤 전달한다.

아직 수행하지 않은 것: 실제 Windows0.4.0 UI/엔진 실행, 실제 계정 모델 호환, 실제 신규 카드 의미 품질/수정 시간/비용·지연 실측. 정의 최종 문구·실제 전송/건수/예산 조건을 확정한 뒤 소수 신규 카드로 별도 시험한다. 모의 성공을 실제 의미 정확도로 보고하지 않는다. 한글 이미지→신규 카드 등록창 드래그앤드롭은 별도 기억 요구사항이며 이번 API 엔진 구현에는 포함하지 않았다.
