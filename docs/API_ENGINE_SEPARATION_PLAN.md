# 베이스화 보존과 신규 카드 API 엔진 분리 계획

작성: 2026-11-06 한국시간. 아래는 승인된 원래 계획이다. 사용자가 모든 제안을 승인해0.4.0에서 구현했다. **실제 API 모델 품질/계정 호환 시험은 아직 수행하지 않았다.** 구현·시험·남은 확인은 [API 엔진 안내](API_ENGINE.md)를 따른다. 원래 계획 상태: **검토용 계획이며 실행 코드 구현 전**.  현재 0.3.9 소스를 대조했다. 기존 베이스화의 사용자 완료 확인은 유지하며, 이 문서는 실제 API 품질이나 새 기능 완료 보고가 아니다.

## 1. 세 영역으로 구분

| 영역 | 역할 | 쓰기 범위 |
|---|---|---|
| 확정 베이스화 | 최초309개 원문/태그/근거, PT의531참조/522경로, 원본 보관·복원 | 기존 등록 및 명시적 사용자 수동 수정 경로만 유지 |
| 신규 카드 API 엔진 | 방법/사례 검색, 의미 판단 요청, 응답 검증, 신규 카드 교정·다음 추천 | API 전용 기록과 검증된 신규 카드의 태그만 |
| 연결부 | 베이스 자료를 읽기 전용으로 제공하고 저장 대상 검증 | 베이스 쓰기를 제공하지 않는 제한된 인터페이스 |

권고 구성은 기존 baseline.py 등을 옮기거나 재작성하지 않고 `bbolprom_engine/api_engine/`에 신규 모듈을 추가하는 방식이다. 예: service / reference_reader / retrieval / definitions / corrections / evidence / repository / provider_bridge. 화면에서도 베이스파일 등록·보관과 신규 카드 API 분석·교정 항목을 구분한다. 프로그램은 하나로 유지한다.

현재 app.py에는 두 기능의 연결 코드가 함께 있으며 API 결과는 Library.save_analysis로 저장한다. 따라서 앱 전체 파일이 이미 독립돼 있다는 설명은 부정확하다. 수정은 새 API 모듈과 app.py의 신규 분석·신규 수동태그 연결부, 필요한 API 설정 화면으로 제한한다. 베이스화 핵심/자료를 수정 대상으로 삼지 않는다.

## 2. 고정할 것과 사용자 예외

- 최초 마스터/카탈로그/매니페스트,309개의 ID·원문·원래 태그/근거·이미지 귀속/순서/바이트를 보존한다. 베이스 분리/재태그/재매핑을 하지 않는다.
- baseline.py와 baseline_edits.py, PT 보관·원본 이미지 저장·기존 이사 경로는 현재 동작을 보존한다. 베이스화 작업은 API 없이 계속 가능해야 한다.
- 사용자 직접 태그 수정과 원본/이전 수정본 복원은 기존 별도 이력을 유지한다. API는 최신 사용자 수정본을 참고할 수 있지만 원본이나 그 수정 이력을 쓸 수 없다.
- baseline_edits.py는 일부 근거 계산에서 api.py.evidence_spans를 사용한다. API라는 파일명만 보고 이 공용 함수를 옮기거나 동작을 바꾸지 않는다. 기존 보안/호출 구성과 공용 함수의 호환성을 유지하며 새 엔진은 어댑터를 통해 사용한다.
- 초기 구현 전에 보호 파일의 SHA와 기준 레코드/연결값을 기록한다. 새 카드와 설정 저장 때문에 전체 SQLite 파일 해시는 변할 수 있으므로, 보호 검사는 DB 파일 전체 해시가 아니라 원본309 레코드와 연결·원본 파일을 대조한다.

## 3. 저장 분리의 권고

**초기에는 기존 library.sqlite3를 유지하고 API 전용 테이블을 추가한다.** 기존309개나 이미지를 다른 DB로 이사시키지 않는다. 새 테이블 예: api_runs / api_tag_editions / api_user_corrections / api_category_definitions / api_reference_index. 실제 이름/세부 스키마는 구현 단계에서 확정한다.

같은 DB이면 신규 카드 태그 적용과 전후 이력·교정 기록을 하나의 트랜잭션으로 처리할 수 있다. DB를 두 개로 나누면 태그만 저장되고 교정 기록은 누락되는 경우를 추가로 해결해야 한다. 폴더나 DB 파일 이름만 분리하는 것보다 쓰기 경계와 원자적 저장이 중요하다.

- 엔진에는 Library/쓰기 가능한 베이스 저장소를 넘기지 않고 입력값과 읽기 전용 참고 스냅샷만 제공한다.
- 저장은 전용 repository를 통한다. 대상이 신규 cards 행인지, 승인 ID/원문 해시가 아닌지, 원문 버전과 사용자 수정 버전이 분석 시작 시점과 같은지 다시 확인한다.
- 쓰기 가능한 테이블을 제한한다. baseline_cards / baseline_image_links / baseline_sources / baseline_tag_editions에는 API 연결로 삽입·수정·삭제할 수 없도록 차단한다. 기존 DB 보호 트리거도 유지한다.
- 결과가 돌아오기 전에 사용자가 원문/태그를 수정했다면 늦은 API 결과를 적용하지 않는다. 기존 사용자 값을 보존하고 오래된 결과로 기록한다.
- 기존 신규 카드의 수동 태그는 보수적으로 보호 상태로 이어받는다. 보호 이유가 불명확한 과거 값을 자동 삭제하지 않는다. 최초309 원본은 마이그레이션 대상이 아니다.
- 키 보관함과 api-safety.sqlite3 일일 원장은 기존 구조를 유지한다. 분석 기록에 키·인증 헤더·전체 공급자 오류 본문을 저장하지 않는다.

## 4. 신규 분석 흐름

신규 원문 → 승인된 방법·분류 정의·관련 베이스/최신 교정 선별 → API 의미 판단 → 코드로 정확한 원문 근거/정책 검증 → 수동 보호와 병합 → 신규 카드 저장·교정 이력.

API가 로컬 프로그램 코드를 직접 실행하는 구조가 아니다. 인계된 정독/부정/준비·수행/주체/정규화/근거 판단 방법을 요청에 제공하고, 의미 판단 결과를 앱이 검사해 적용한다. 기존19정책·승인 절차·출처 있는 방법론 연결을 유지한다. 자동 처리 결과는 공통 승인 정답으로 자동 승격하지 않는다.

309개 전체나 PT/이미지를 매 요청에 보내지 않는다. 관련 사례 전송 동의/기존 상한을 유지하고 필요한 자료만 선택한다. 교정 원문도 외부 참고에 사용되는 범위를 설정에서 설명한다. 참조에는 카드ID·원문해시·수정 버전·규칙 버전을 기록해 과거/철회/대체 사례를 구분한다.

## 5. 이전 제안의 반영 범위

1. **분류 정의와 경계:** 인계의 확정 문구와 미확정 내용을 대조해 정의/포함/제외/인접분류 경계 초안을 제시한다. 신규 분석용 승인 버전을 기록하며 원본309 분류를 재계산하지 않는다. 최종 정의 문구는 사용자 확인 후 사용한다.
2. **수동 수정·제외 보호:** 새 카드의 자동 후보/수동 확정/사용자 제외를 구분한다. 재분석이 수동 태그를 지우거나 제외 태그를 되살리지 않도록 병합한다. 원문이 바뀌어 근거가 무효가 되면 표시·검토 대상으로 남기고 허위 근거를 만들지 않는다.
3. **한영 검색:** 승인된 영문 근거와 한글 태그ID를 잇는 로컬 색인을 사용한다. 단순 문자열 일치의 약점을 보완하고 관련 사례만 제공한다. 추가 유료 임베딩/검색 호출을 기본으로 넣지 않는다.
4. **반복 근거:** 더 긴 정확한 인용이나 검증 가능한 문맥으로 위치를 구분한다. 좌표는 코드가 계산하며 모호한 반복의 첫 위치를 임의 선택하지 않는다. 신규 응답 검증을 별도로 확장하고 원본309의 기존 구간·예외는 보존한다.
5. **교정의 다음 추천 반영:** 수정 전후·원문 버전·근거·대상 범위·활성/철회 상태를 기록한다. 다음 유사 카드에 유효한 관련 교정만 제한적으로 참고한다. 모델 가중치 재학습과 구분한다. 한 카드의 예외를 전체 규칙으로 바꾸는 승격은 사용자 확인을 받는다.
6. **API 변경 이력과 백업 부담:** 태그만 바뀐 API 작업은 전후 태그 이력을 트랜잭션으로 저장하고 매번 대용량 원본을 복제하지 않는 방향을 제안한다. 기존 전체 백업과 원본/vault/보존·삭제 정책은 유지한다. 태그 이력은 전체 원본 백업의 대체품이 아니며, 공용 저장소/전체 복원 UI 재설계는 별도 범위다. API 전용 테이블도 기존 DB 스냅샷 백업에 포함되는지 검증한다.

개별 API 태그마다 추가 승인 팝업을 강요하는 흐름은 새로 넣지 않는다. 검증된 자동 결과는 신규 카드에 적용하고, 사용자 수동 수정은 보호한다. 분류 정의 확정·공통 규칙 승격·외부 전송/유료 시험 조건처럼 별도 판단이 필요한 경계만 확인한다.

## 6. 순서와 통과 기준

1. 보호 대상/버전 기록과 쓰기 경계부터 구현한다. 신규 모듈/설정 플래그를 추가해 실제 호출 없이 분리 시험을 한다. 업그레이드만으로 유료 호출이 시작되지 않게 한다.
2. 신규 수동 보호·교정 원장·API 태그 이력과 저장을 연결한다. 기존 신규 카드/수정 이력의 보수적 이어받기를 임시 라이브러리로 검증한다.
3. 정의 초안과 한영 조회, 반복 근거, 교정 선별을 모의 API로 종단 검증한다. 분류 정의 확정은 사용자 검토와 병행한다.
4. 두 검사 묶음을 독립 보고한다. **베이스 보존:** 보호 파일SHA/309 원문·원래 태그·10358근거/17예외/531순서참조/522경로/원본 바이트, 같은 원문12그룹과109·110·188, 사용자 수정 이력, 등록/보관/재시작/백업. **API 동작:** 수동 보호/제외/철회/버전 충돌/반복 근거/잘못된 JSON/실패·타임아웃·중복 저장/비용 원장/키 비노출.
5. API 분류 정의·사용 모델의 실제 계정 접근/단가·전송 범위/건수/금액을 확인한 뒤 소수 신규 카드로 실호환성 및 품질 시험을 한다. 모의 응답이나309 정답 참조를 실제 신규 카드 정확도로 보고하지 않는다. 추가 유료 검토 루프는 자동 도입하지 않는다.
6. 변경분 패치로 전달한다. 패치에는 프로그램 변경만 담고 사용자 data를 넣지 않는다. 새 API 테이블 추가는 최초 실행 시 필요한 것만 수행하고 베이스 테이블은 재작성하지 않는다. 적용/기능 끄기/태그 되돌리기와 기존 프로그램 호환성을 검증한다.

실제 품질 합격선과 실호출 금액은 아직 확정하지 않았다. 현재 턴은 계획 기록뿐이며 코드/DB/EXE 변경·신규 시험·실API 호출은 없다.
